# EPP+KEDA+FMA Benchmark Report

Three actuation paths for **`Qwen/Qwen3-14B`**, measured under KEDA
[queue-based][queue-guide] autoscaling with load generated by
**[inference-perf][inference-perf]**. All three passes differ only in **who owns
the model-server lifecycle**:

[inference-perf]: https://github.com/kubernetes-sigs/inference-perf

| Pass | Model load |
|---|---|
| **Baseline** | Cold — a new decode pod loads the model on every scale-up |
| **Warm** | FMA launcher already running; scale-up creates a new vLLM instance |
| **Hot** | All replicas pre-loaded during standup, then scaled to 1 (vLLM sleeps); scale-up wakes a sleeping instance |

Run on an NVIDIA H100-80GB-HBM3 OpenShift cluster, one GPU per replica. Every
metric reported below is defined in [Metric Definitions](#metric-definitions).

> [!NOTE]
> Values in the results table are **3-run averages**, so small differences
> between columns should not be read as significant. All three passes used
> identical workload, model, and autoscaling configuration — only the
> model-server lifecycle owner differs.


These three passes use the autoscaling setup from
[keda-epp-queue][queue-guide] — KEDA polling the EPP
`llm_d_epp_flow_control_queue_size` and `llm_d_epp_request_running` gauges, EPP
`flowControl` feature gate on, the optimized-baseline scheduler plugins, and a
KEDA-generated HPA on the scale target.

[queue-guide]: ../../../workload-autoscaling/keda-epp-queue/README.md

## Shared Prefix Heavy (Long)

> 4,256 input tokens (4,000-token shared prefix + 256-token question) · 1,000
> output tokens · 2 RPS for 120 s, then 12 RPS for 900 s · 32 client workers

Prompts are drawn from 128 shared prefixes × 128 questions each, so the 4,000-token
prefix is reused across requests and is cacheable — this is a prefix-cache-heavy,
prefill-dominated workload. The 900 s heavy stage ("Long") runs well past the
scale-up ramp, so the run covers steady-state serving and not just actuation.

### Configuration

The [keda-epp-queue][queue-guide] configuration, with `maxReplicaCount` lowered
to 6. Thresholds, polling interval, trigger queries, metric source, and plugin
set are the guide's defaults.

| Component | Parameter | Value |
|---|---|---|
| Model | Name | `Qwen/Qwen3-14B` |
| Model | Tensor parallelism | 1 (1 GPU per replica) |
| Workload | Load generator | `inference-perf` |
| KEDA | Trigger 1 — queue size threshold | `1` |
| KEDA | Trigger 2 — running requests threshold | `16` |
| KEDA | Polling interval | 15 s |
| HPA | Min / Max replicas | 1 / 6 |
| HPA | Scale-up | 0 s stabilization, 1 Pod / 30 s |
| HPA | Scale-down | 300 s stabilization, 1 Pod / 300 s |
| Idle replicas | Baseline / Warm / Hot | 1 decode pod / 1 requester / 6 requesters pre-loaded, then scaled to 1 |

Pod startup 124.7 s → 71.0 s → 3.3 s: with FMA hot-start, autoscaling relief
arrives ~37× faster. **P95 TTFT falls 97%** (51.9 s → 1.5 s) and mean latency
60% (67.9 s → 27.1 s), and both FMA paths completed all 11,040 requests in every
run while baseline shed 752 on average.

Replica count is not the lever here — all three passes sit near the ceiling of 6
(4.95 → 5.22) — so the gain comes from capacity arriving sooner, not from running
more pods. What the ramp costs is not recovered later: baseline enters steady
state with a deep backlog and never drains it, holding a flow-control queue of
126.0 against ~1 for the FMA paths. Its mean ITL is also ~2× higher (49.4 vs
~26 ms/tok) — a per-token decode rate, measured after a request is already
admitted — so at equal replica counts baseline was serving in a degraded regime
for the whole window, not merely starting late.

## Metric Definitions

`llm_d_epp_flow_control_queue_size` is the KEDA scale trigger here, with
`llm_d_epp_request_running` as the second trigger. The other EPP gauges are
reported for comparison with the saturation-based results.

| Metric | Definition |
|---|---|
| Duration | Wall-clock length of the benchmark window (s) |
| Total requests | Requests issued by the harness over the run |
| Mean / P95 latency | End-to-end request latency, request sent to last token (ms) — mean and 95th percentile; lower is better |
| Mean / P95 TTFT | Time-to-first-token (ms) — mean and 95th percentile; lower is better |
| Mean / P95 ITL | Inter-token latency between consecutive generated tokens (ms/token) — mean and 95th percentile; lower is better |
| Avg replicas | Mean ready pod count during the test window |
| Max replicas | Peak ready pod count; 6 means the `maxReplicaCount` ceiling was reached |
| Avg KV cache utilization | Mean GPU KV cache utilization across serving replicas |
| Avg queue depth (EPP) | Mean pending-request queue depth at the endpoint proxy |
| Avg flow-control pool saturation (EPP) | Mean `llm_d_epp_flow_control_pool_saturation`; >1.0 means the pool is overloaded and throttling |
| Avg flow-control queue (EPP) | Mean EPP flow-control queue size |
| Avg running requests (EPP) | Mean `llm_d_epp_request_running` — in-flight requests across the pool |
| Avg pod startup | Mean time for a new replica to become ready and serve (s) — lower is better |
| Hot hit rate | Share of run-phase FMA actuations that woke a sleeping vLLM (`wake`) |
| Warm hit rate | Share of run-phase FMA actuations that created a new vLLM on an existing launcher (`create_instance`) |
| Failures | Requests that did not complete successfully |
| Δ% Hot vs Baseline | Relative change from the Baseline column to the Hot column; sign follows the raw value, so a negative delta is an improvement for the latency, queue, and startup metrics |
