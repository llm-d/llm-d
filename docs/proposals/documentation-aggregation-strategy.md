# Distributed Documentation Aggregation Strategy

##  Summary
We need to enhance our current remote documentation system to better scale as we add more repositories and components. Currently, we manually configure each file using `docusaurus-plugin-remote-content`, which works well but needs enhancements for broader documentation coverage and versioning support.

## Background
Our documentation website (llm-d.ai) is built using Docusaurus with the `docusaurus-plugin-remote-content` plugin to pull documentation files from different GitHub repositories. We have a well-structured system with:

- Centralized component configurations in `component-configs.js`
- Individual remote content sources for specific files
- Content transformation system that handles MDX compatibility and links
- Automated frontmatter and source attribution

## Current Setup Assessment

Our existing system works well with:
- **Individual File Specification**: Each remote content source targets specific files (like README.md)
- **Centralized Configuration**: All repository information managed in `component-configs.js`
- **Content Transformation**: Unified transform system that points all relative links back to GitHub
- **Component-Based Organization**: Architecture, Guide, and Community sections with autogenerated sidebars

## Proposed Enhancements

### Enhancement 1: Automatic Documentation Discovery
Extend our existing remote content system to automatically sync all `*.md` files under the `docs/` directory for each component repository.

### Enhancement 2: Docusaurus Versioning Support  
Implement versioning based on release information from GitHub releases, allowing documentation to be available for specific versions (e.g., v0.2.0) based on component version tables in releases.

## Requirements

**Enhancement 1 Requirements:**
- Extend existing remote content generators to include all `*.md` files from `docs/` directories  
- Preserve existing transformation system and autogenerated sidebars
- Build on existing `component-configs.js` system

**Enhancement 2 Requirements:**
- Parse component version tables from GitHub release pages (handling mixed versioning)
- Create version-specific remote content configurations using actual component tags
- Support version dropdown navigation while excluding deprecated/external components

**Technical Constraints:**
- Respect GitHub API rate limits
- Maintain backward compatibility with current remote content configurations
- Work within existing Docusaurus + `docusaurus-plugin-remote-content` architecture

## Versioning Strategy

Analysis of the [v0.2.0 release](https://github.com/llm-d/llm-d/releases/tag/v0.2.0) reveals complex component versioning:

**Mixed Component Versions Example:**
- `llm-d-inference-scheduler`: v0.2.1 (different patch version)  
- `llm-d-routing-sidecar`: v0.2.0 (matches release)
- `llm-d-inference-sim`: v0.3.0 (different minor version)
- `llm-d-infra`: v1.1.1 (completely different major version)
- Some components marked as "NA (Deprecated)" or external dependencies

**Implementation Approach:**
1. Parse release component tables to extract actual version tags for each component
2. Create version-specific remote content configurations using component-specific tags (not uniform release tags)
3. Exclude deprecated ("NA") components and external dependencies
4. Present unified "v0.2.0" version to users while pulling from different component tags behind the scenes

## Implementation Results

**Enhanced Documentation Coverage:**
- All `*.md` files from component `docs/` directories automatically included
- Version dropdown with component-specific version tags
- Maintains current navigation: `What is llm-d? | User Guide | Community | News`

**Enhanced Structure Example:**
```
docs/architecture/Components/
├── inference-scheduler.md           # README.md (current)  
├── inference-scheduler/            # NEW: docs/ directory content
│   ├── api-reference.md            # From docs/api-reference.md
│   ├── configuration.md            # From docs/configuration.md
│   └── troubleshooting.md          # From docs/troubleshooting.md
└── [other components with full docs trees]
```

**Version Example (v0.2.0):**
- Components use their specific release tags (v0.2.1, v0.3.0, v1.1.1, etc.)
- Users see unified "v0.2.0" version dropdown
- Deprecated and external components automatically excluded

### Documentation Standards for llm-d Contributors

To minimize transformation complexity and avoid edge cases, follow these standards that align directly with our current transformation system in `repo-transforms.js`.

#### Repository Structure Standard

```
Component repository:
├── README.md              # Component overview (currently auto-synced)
├── docs/                  # ENHANCED: All .md files will be auto-synced
│   ├── installation.md    # NEW: Will be automatically included
│   ├── api-reference.md   # NEW: Will be automatically included
│   ├── configuration.md   # NEW: Will be automatically included
│   ├── images/           # Store images in docs/ for consistency
│   └── assets/           # Alternative location for assets
├── examples/             # Not included in docs (stays in repository)
└── [other repository content]
```

#### Version Compatibility Standards

**For Enhanced Versioning Support:**

- **Individual Component Versioning**: Each component may have different version tags (e.g., v0.2.1, v0.3.0, v1.1.1) within the same release
- **Stable Paths**: Keep image and link paths consistent between versions to support mixed versioning
- **Release Table Accuracy**: Ensure component versions in release tables accurately reflect the actual git tags
- **Documentation State Consistency**: Documentation should reflect the component state at its specific version, not the overall release version
- **Deprecation Handling**: Mark deprecated components clearly and exclude them from version-specific documentation builds

#### Markdown Standards

**✅ Callouts - Use GitHub-Style (Auto-Converted)**
```markdown
<!-- These are automatically converted to Docusaurus admonitions -->
> [!NOTE]
> This is a note that will become :::note in Docusaurus

> [!TIP] 
> This tip will become :::tip in Docusaurus

> [!IMPORTANT]
> This becomes :::info in Docusaurus

> [!WARNING]
> This becomes :::warning in Docusaurus

> [!CAUTION]
> This becomes :::danger in Docusaurus
```

**✅ HTML Tags - Use Self-Closing Format**
```markdown
<!-- CORRECT: Self-closing tags work without transformation -->
<br />
<img src="./image.png" alt="Description" />

<!-- AVOID: These require transformation -->
<br>
<img src="./image.png" alt="Description">
```

**✅ Images - Use Relative Paths**
```markdown
<!-- RECOMMENDED: Relative paths are automatically converted to GitHub raw URLs -->
![Architecture Diagram](./docs/images/architecture.png)
![API Flow](./images/api-flow.svg)
![Example](../assets/example.jpg)

<!-- These become: https://github.com/org/repo/raw/branch/docs/images/architecture.png -->
```

**✅ Links - Use Relative for Repository Content**
```markdown
<!-- RECOMMENDED: Relative links automatically point to GitHub -->
[Installation Guide](./docs/installation.md)
[API Reference](./api-reference.md)
[Examples](../examples/README.md)

<!-- These become: https://github.com/org/repo/blob/branch/docs/installation.md -->

<!-- For external llm-d components, use full GitHub URLs -->
[llm-d Scheduler](https://github.com/llm-d/llm-d-inference-scheduler)
```

**✅ Code and JSON - Avoid Inline JSON Objects**
```markdown
<!-- RECOMMENDED: Use code blocks for JSON -->
```json
{
  "config": "value",
  "setting": 123
}
```

<!-- AVOID: Inline JSON that requires escaping -->
Configure with {config: "value", setting: 123}
```

#### Standards to Prevent Common Transformation Issues

**🚫 Avoid These Patterns (They Require Extra Transformations)**

```markdown
<!-- AVOID: Non-self-closing HTML tags -->
<details>
<summary>Click to expand</summary>
Content here
</details>

<!-- AVOID: Complex nested JSON in text -->
Set the config to {nested: {value: "data"}} in your file.

<!-- AVOID: Angle bracket URLs -->
Configure at <https://example.com/config>

<!-- AVOID: Unquoted HTML attributes -->
<img src=image.png alt=description>
```

**✅ Use These Instead**

```markdown
<!-- CORRECT: Simple details/summary -->
<details>
<summary>Click to expand</summary>

Content here

</details>

<!-- CORRECT: Code formatting for complex data -->
Set the config in your file:
```json
{
  "nested": {
    "value": "data"
  }
}
```

<!-- CORRECT: Standard markdown links -->
Configure at [the config page](https://example.com/config)

<!-- CORRECT: Quoted attributes -->
<img src="image.png" alt="description" />
```
